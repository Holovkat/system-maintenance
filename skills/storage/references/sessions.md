# Resumable cleanup sessions

For normal deep discovery use [the automatic runner](automatic.md). The manual
attach/triage commands below remain low-level interfaces for explicitly requested
investigation and existing sessions; they are not an agent-authored substitute
for the one-invocation collector → System 1 → report flow.

Use the existing `storage.py audit --save` collectors and native cleanup engine.
`scripts/storage_session.py` (plugin-root relative) owns the checklist and gates.
The toolbox also routes `system_maintenance.py session ...` from any directory.
Small state files live beside reports/plans/receipts under System Maintenance's
state root; `--state-dir` allows controlled fixtures. Never use a global last
report/session to bind another chat's approval.

## Start and continue

```bash
python3 <plugin>/scripts/storage_session.py create \
  --goal "Recover disposable storage; preserve databases, logs and wanted models" \
  --keep /exact/preserved/path --keep custom-model:tag
python3 <plugin>/scripts/storage_session.py next --session SESSION_ID
python3 <plugin>/scripts/storage_session.py status --session SESSION_ID
```

Default sections cover caches, Docker images/containers/volumes, models, external
storage and closeout. `create --sections ... closeout` selects a smaller checklist.
`next` is a read-only routing hint, never permission to act. Resolve ordinary
inspection choices; ask about retention, later downloads/rebuilds or interruption,
not whether to investigate the next section. One writer owns mutations. Authorized
specialists can return section evidence to that writer; they do not independently
retry rubric calls or execute cleanup.

For each section, inspect ownership, contents, active use, recovery route and
resource references. Make a section-specific saved audit; account for every row.
Never infer disposable data from age, names or lack of container references alone.
Files containing credentials or private data remain outside model context.

Attach an observations JSON file using this shape. Facts are inspection claims,
not proof generated by the model; reference the actual inspection artifacts.

```json
{
  "candidates": [{
    "id": "PATH-from-the-saved-audit",
    "facts": {
      "owner": "Owning application established by inspection",
      "content_class": "cache",
      "activity": "inactive",
      "recovery": "redownload",
      "notes": "Evidence-based description; no secrets or shell commands",
      "evidence_refs": ["/absolute/inspection.json"]
    }
  }]
}
```

Content is `cache`, `empty`, `database`, `logs`, `installed_model` or `unknown`.
Activity is `inactive`, `active` or `unknown`; recovery is `redownload`, `rebuild`,
`not_needed` or `unknown`. Unknown facts cause a visible evidence gap. Database,
log and installed-model rows and explicit keep selections are retained by hard
rules, not ranked away. For wanted removals outside these preservation defaults,
stop for a separately scoped workflow; do not relabel data as cache.

```bash
python3 <plugin>/scripts/storage_session.py attach --session SESSION_ID \
  --section caches --report REPORT_ID --observations /absolute/observations.json
python3 <plugin>/scripts/storage_session.py retain --session SESSION_ID \
  --section caches --ids CANDIDATE_ID --reason "Owner chose to keep this"
python3 <plugin>/scripts/storage_session.py triage --session SESSION_ID --section caches
```

## System 1 rubric and fallout

Only the stable JEV gateway `/v1/decision` is used (default origin
`http://127.0.0.1:8096`; `JEV_BASE_URL` may identify another gateway origin).
No provider/model selection or upstream fallback is exposed. Each section uses
one packet containing independently indexed candidate contexts and a shared
versioned rubric. Actual paths, commands, inspection file contents and owner
approvals remain outside model context; references are opaque evidence IDs.

Choice questions classify readiness, missing evidence and the next owner
question. **Every Choice payload ends with `fallout`: none of the preceding
options is acceptable or adequately supported.** This is a real selectable
answer, not a post-processing exception or forced nearest match. Any fallout
answer stops the section and records a `rubric_fallout` review item. Noul
predicates additionally assess evidence sufficiency and rubric coverage; they
are supporting signals, not permission.

Choice probabilities/confidences and Noul probabilities use the gateway's 0–1
scale and are shown in reports. There is **no invented default passing score**.
Scores are advisory unless the owner supplies a calibrated cutoff with
`create --minimum-support NUMBER`. That explicit policy is then bound into
packets/approvals and gates all Choice and positive Noul support values. In
either mode, supported readiness, positive sufficiency/coverage predicates,
no stated evidence gap, and deterministic ownership/content/activity/recovery
and preservation checks are required. Contradictory answers, missing results,
unknown values, malformed distributions, timeouts and unavailable services
never become approvals. A rubric result still needs exact owner approval.

The exception queue records candidate/section, failure kind, available evidence
references, missing information and a recovery/review route. A service or contract
failure is a process-improvement review item as well as a section blocker.
Missing facts route to more inspection. Rubric fallout/gaps and conflicts route
to review, which may identify more evidence or an explicitly approved alternative;
the tool does not silently substitute another decision system.

Unchanged successful packets are reused; unchanged failed packets are not retried.
A retry needs changed observations or a bounded artifact demonstrating recovery:

```bash
python3 <plugin>/scripts/storage_session.py triage --session SESSION_ID \
  --section caches --recovery-evidence /absolute/gateway-recovery.json
python3 <plugin>/scripts/storage_session.py review --session SESSION_ID \
  --review REVIEW_ID --resolution "Explanation of process correction" \
  --evidence /absolute/correction-evidence.json
```

Recovery leaves the original item `recovered_review_pending`; it never deletes
the failure. Resolving a review annotates history, not a rubric result or owner
approval. Interrupted provider calls have a persisted started attempt. Interrupted
cleanup stays unresolved with its per-resource journal; `run` never replays it.
Reconcile changed resources, record evidence, and keep/defer the affected section
before using a new session for any remaining removals.

## Plan, owner approval and execution

```bash
python3 <plugin>/scripts/storage_session.py plan --session SESSION_ID \
  --section caches --select CANDIDATE_ID
python3 <plugin>/scripts/storage_session.py approve --session SESSION_ID \
  --section caches --plan PLAN_ID --owner "Owner name" \
  --source "Reference to the owner's explicit approval of these exact items"
python3 <plugin>/scripts/storage_session.py run --session SESSION_ID \
  --section caches --plan PLAN_ID
```

`approve` records existing owner consent; the agent cannot grant it from a
favourable rubric. Session policy, packet, evidence hashes, plan identity and
expiry bind approval. Replacing evidence/selection invalidates it. Native
preflight still rechecks live resources immediately before mutation. Completed
runs return their receipt without repeating deletion. Unselected rows remain
untouched. Use `mark --outcome kept|deferred --reason ...` for owner decisions
to stop work on an entire section; these outcomes are not verified removals.

Only adapters already supported by `storage.py` execute. Container recreation,
selective Docker image removal with exclusions and volume retirement must not
be improvised into shell actions through this session tool. Preserve evidence
and raise an adapter-gap review when required support is absent. Broad image
pruning is blocked when session exclusions exist. Native-managed stores remain
protected from path deletion. There is no blanket system/volume prune.

## Report and stop

```bash
python3 <plugin>/scripts/storage_session.py report --session SESSION_ID --refresh
python3 <plugin>/scripts/storage_session.py close --session SESSION_ID
```

Reports render checklist, measured/estimated candidate sizes, exact owner
approvals, execution receipts, outstanding reviews and baseline/latest free
space per drive. They distinguish removed contents from observed capacity
change, avoid additive shared-size promises, and expose kept/deferred sections.
Only receipt-backed successful execution becomes `verified`; remaining work
prevents closeout. Closeout can still show explicitly deferred obligations and
unresolved process-review items—present them, never label them passed.

Stop when the requested goal and its evidence are satisfied, or only owner
decisions remain. Do not continue low-value investigation merely to empty every
folder or exhaust the checklist.
